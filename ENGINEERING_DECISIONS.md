## Phase 1 security decisions (2026-11-13, session 9)

| ID | Decision | Rationale (evidence) |
|----|----------|----------------------|
| ED-P1-1 | Master-switch OFF denies every privileged route EXCEPT the control plane: health (public), switches GET/PATCH, and the new `GET /api/v1/auth/verify` ("login"). Master-OFF also cascades: microphone + camera forced OFF, running agents paused, world state to standby | Part 13 "Everything except health and login denied" — a literal reading with no carve-out would make Master OFF an unrecoverable lockout (the owner could never switch back on). Mirrors the FastAPI CORE cascade semantics; carve-out is the minimal login surface. Proven: phase1_e2e 48/48 |
| ED-P1-2 | Rate limiting is in-memory per process: 5 auth failures/60 s/IP → 429 + Retry-After (FastAPI CORE policy), plus a 240 req/60 s/IP general cap | Single-instance Railway deployment — per-process == per-instance today. Limitation documented: a multi-instance future needs a shared store; spoofed-XFF evasion is blunted in production because the Railway proxy sets X-Forwarded-For. The owner key (constant-time) remains the primary control; the limiter blunts brute force and scraping |
| ED-P1-3 | The guard reads the Master switch fresh from the database on every request (async guard; all 27 call sites in 21 route files now await it) — no cache, no TTL window | A TTL cache was rejected during implementation: it opens a one-request enforcement hole after every cold start and after every TTL expiry. Fresh reads make Master-OFF take effect on the very next request |
| ED-P1-4 | Owner-key verification endpoint `GET /api/v1/auth/verify` added; OwnerGate panel now verifies against it instead of `GET /api/v1/agents` | With Master OFF, agents GET is denied — the unlock panel needs a stable login endpoint that survives Master OFF (Part 13 "login"). The endpoint returns only `{ok, verified_at}` — no data exposure |
| ED-P1-5 | Backup/restore ports the hardened FastAPI semantics: strict schema validation (unknown tables/fields/types → 400), 4 MiB cap → 413, dry-run, automatic pre-restore safety backup, ATOMIC restore (deletes+creates+count verification in one interactive transaction — any failure rolls back completely), secrets excluded by policy, sensitive memory contents redacted in exports | Part 14 "A backup must be restored and verified on a separate copy" — proven in phase1_e2e §9: payload restored into a COPY of the database on a second server instance and verified against the backup counts |
| ED-P1-6 | Switch enforcement points: microphone → asr + voice-modality send; camera → vision-modality send; embodiment → embodiment-specific world modes (holographic_presence, digital_human_embodiment — the FastAPI set); computer_control → ALL tool execution in conversations/send (honest spoken block notice, never silent); autonomy → direct owner requests remain allowed (dispatch BY the owner is a direct request; no self-initiated server work exists yet — enforcement lands with the Phase 14 mission system); remote_compute → enforcement point documented for the future worker dispatch queue | Part 13 OFF-behaviour table. Each gate proven in phase1_e2e §3–§6. The blocked-tool reply states the block — the honesty guard extended to switch enforcement |
| ED-P1-7 | Guard E2E (Gate 0 matrix) probes now send unique X-Forwarded-For client IPs | The Phase 1 rate limiter (correctly) locks out the 24+ anonymous probes of the old matrix after 5 failures. Unique IPs exercise the production proxy path and keep the auth matrix meaningful; lockout behaviour itself is proven in phase1_e2e §11 |
| ED-P1-8 | `db/custom.db` (dev database) is never used as the E2E baseline; Phase 1 E2E boots from a schema-only fresh DB so cold-boot seeding proves the default-OFF microphone/camera switches | The dev DB carries session state (mic ON from earlier sessions) — defaults must be proven from a genuinely fresh boot (Part 13: mic/camera default OFF on every new session and restart) |
